# Logical Data Model

This document is the authoritative logical schema baseline. Migrations may refine physical details, but they must preserve the ownership, relationships, invariants, and constraints defined here.

## Global conventions

### Identity and tenancy

- Business identifiers are UUIDs generated by the application or PostgreSQL.
- Every office-scoped table contains `office_id NOT NULL`.
- Parent tables expose `UNIQUE (office_id, id)`; office-scoped foreign keys use `(office_id, foreign_id)` to prevent cross-office references.
- Public identifiers are never sequential database keys.
- `office_id` is derived from the authenticated session, never accepted as an unrestricted client value.

### Audit columns

Mutable business records contain:

```text
id, office_id
created_at, created_by
updated_at, updated_by
version
archived_at, archived_by
```

`version` starts at 1 and increments on every successful mutation. API writes require the expected version.

Immutable records contain `created_at` and `created_by` but no ordinary update/archive columns. Corrections use a new amendment, reversal, void, or status event.

### Time

- Instants use `timestamptz`; PostgreSQL normalizes them and the application treats them as UTC.
- Date-only clinical and office-business dates use Gregorian `date`.
- Durations use integer minutes unless a domain requires a more precise unit.
- The office timezone is an IANA identifier in office configuration; v1 defaults to `Asia/Tehran`.
- Jalali values are presentation/input values and are never stored as domain dates.
- The office business date is calculated by one shared service from the authoritative instant and configured office timezone.

### Money

- v1 stores money as signed `bigint` rials in columns named `*_amount_rial` or `amount_rial`.
- Toman is an input/display unit only. The issued display unit is snapshotted where a receipt, plan, or statement must be reproduced.
- API money values are decimal strings, for example `{ "amountRial": "12500000" }`; generated clients convert them to `bigint`.
- Floating-point values are prohibited in financial calculations.
- Multi-currency is outside v1 and requires a replacement ADR and migration.

### Text and normalization

- Original entered names, phones, identifiers, and addresses are retained.
- Search-normalized values are stored separately and may be regenerated by a versioned normalization algorithm.
- Static UI text does not live in the database. Runtime-editable catalog/template content uses stable base rows and `*_translation` rows; v1 requires `fa-IR` rows only.

### Status values

Business status values are stable English codes controlled by migrations or domain code. A generic user-editable status table is prohibited for appointment, encounter, plan, journey, lab, document, communication, ledger, merge, outbox, or audit lifecycles.

Rotation rewrites records to the active key version; logout, revocation, expiry, and session cleanup delete or cryptographically erase token material while retaining non-secret audit facts. System administrators do not receive clinical permissions implicitly. Disabling a user preserves historical authorship.

## Scheduling

| Table | Key fields and constraints |
|---|---|
| `appointment` | patient, provider, operatory, type, start instant, duration, timezone snapshot, reason, status, confirmation state, version |
| `appointment_status_event` | appointment, previous/new status, actor/time, reason, replacement appointment; append-only |
| `appointment_conflict_override` | appointment, conflict type, conflicting IDs, actor/time, reason; append-only |
| `appointment_type` | stable office code, name translation, default duration, active state |
| `appointment_resource_reservation` | appointment, provider-or-operatory resource, `tstzrange`, exclusive flag, optional override; active exclusive rows use a GiST exclusion constraint per office/resource |
| `appointment_procedure` | appointment, optional planned appointment and treatment-plan item, procedure/anatomy/provider/duration/journey snapshots; unique appointment/plan-item where linked |
| `provider_availability` | provider, effective range, weekday/time range, timezone |
| `schedule_block` | provider and/or operatory, time range, reason, actor |
| `planned_appointment` | patient, source context, target date/range, procedure snapshot, provider preference, status |
| `waitlist_entry` | patient, preferences, priority, expiry, status, version |
| `waitlist_contact_attempt` | entry, channel, outcome, actor/time; append-only |
| `recall_definition` | patient, type, interval policy, provider preference, communication policy, active state |
| `recall_instance` | definition, due/grace dates, linked appointment, status, version |

Authoritative conflict checking occurs inside one Scheduling transaction. The application locks the affected resources in stable order, evaluates availability/closures/holidays and soft policy conflicts, then writes provider and operatory reservations. PostgreSQL exclusion constraints are the final guard against overlapping exclusive reservations. An authorized override creates an append-only override record and a non-exclusive reservation only for conflict types the approved policy declares overridable; hard conflicts remain non-overridable. Reschedule updates reservations atomically. Tests cover simultaneous create/reschedule requests and intervals spanning midnight.

## Patient Finance

| Table | Key fields and constraints |
|---|---|
| `ledger_entry` | patient, business date, occurred/posted times, entry type, signed `amount_rial`, source type/ID, reason, original entry, approval; immutable after posting |
| `payment_allocation` | payment entry, charge entry, `amount_rial`; positive amount, unique payment/charge pair |
| `finance_approval` | action type/target, requester, approver, decision/time, reason; requester and approver differ when separation is required |
| `receipt` | payment/transaction reference, immutable office receipt number, issued time, display unit, content hash, void state |
| `receipt_event` | receipt, issue/void/reissue event, actor/time, reason; append-only |
| `day_end_close` | office business date, sequence, canonical totals, actor/time, content hash; immutable |
| `credit_transfer` | source/destination patient and paired ledger entries; source and destination differ |

Sign convention:

- Charge and refund increase the patient balance and are positive.
- Payment and discount decrease the patient balance and are negative.
- Adjustment explicitly declares debit/credit direction.
- A reversal references exactly one original entry, uses the exact negated amount, and is unique per original entry unless the original reversal was itself validly reversed.
- Allocations are positive magnitudes, cannot exceed the absolute payment or outstanding charge, and are validated transactionally.
- Balance is the sum of posted `ledger_entry.amount_rial`; it is never stored as an editable field.

Database roles deny ordinary `UPDATE` and `DELETE` on posted ledger entries. The application uses append-only functions/repositories for posting and reversal.

## Index baseline

- Patient normalized name, mobile, identifier, email, and patient number.
- Appointment resource/time range, provider/operatory/start/status, treatment-item links, and patient/start.
- Open planned appointments, waitlist, recall, tasks, journeys, and lab orders by due/expected date.
- Clinical timeline by patient and authoritative time.
- Ledger by patient/business date/posting time; allocations by payment and charge.
- Outbox unpublished rows by available time; processed-event unique key; open event gaps by deadline.
- Audit by patient, actor, entity, action, and time.
- Documents and communications by patient/time/state.

Indexes are validated with representative volumes and query plans; speculative indexes are not added without an observed query.

## Deletion, retention, and legal hold

- Signed clinical records, posted ledger entries, issued receipts, consent acknowledgments, and audit events are never hard-deleted through ordinary product behavior.
- Mutable configuration and operational records are archived when business history requires retention.
- Retention jobs operate only after jurisdiction-specific periods and legal-hold behavior are approved.
- Object deletion is a two-phase audited process: mark eligible in PostgreSQL, delete/version-expire the object, then record completion.
- Patient merge is not deletion. Privacy correction of demographics preserves clinical authorship and financial history.

## Concurrency and database enforcement

- Mutable records use optimistic concurrency through `version` and API `If-Match`.
- Financial posting, allocation, receipt numbering, day close, patient merge, and appointment conflict checks use explicit transactional locking appropriate to the invariant.
- Signed clinical and posted financial immutability is enforced by database privileges/constraints in addition to application rules.
- Constraint violations map to stable domain error codes; raw database errors are never returned to clients.
